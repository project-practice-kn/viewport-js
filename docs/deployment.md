# Запуск и обслуживание

TrueNAS + существующий Traefik (`proxy`, `websecure`, resolver `le`, `calendar.samuraj.su:4443`) описан в отдельном [гайде](truenas.md) с [production Compose](../compose.truenas.yaml). Ниже — локальный запуск и обслуживание.

## Первый запуск

Создайте `.env` со случайными секретами, затем поднимите весь проект:

```sh
node scripts/setup-env.mjs
docker compose up --build -d --wait
```

Без установленного Node.js первую команду можно выполнить контейнером:

```sh
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/workspace" -w /workspace node:24-bookworm-slim node scripts/setup-env.mjs
```

Приложение: **http://localhost:5173**. S3: `http://localhost:8333`, bucket приватный. Порты опубликованы только на loopback. Секреты передаются при запуске через `.env`, исключённый из build context; в образ они не копируются. Не публикуйте вывод `docker compose config`/`inspect` с environment.

Приложение ждёт healthy S3, выполняет миграции и настройку bucket/CORS, затем запускает production-сборку. Ошибка подготовки останавливает запуск. `/health` проверяет доступность таблиц мигрированной SQLite; Compose проверяет его раз в пять секунд. Runtime работает пользователем node, не root.

Регистрация доступна только по коду `REGISTRATION_INVITE_CODE` из `.env`. Скрипт подготовки генерирует отсутствующий код, сохраняя существующие секреты; сам код не выводится в лог. Организатор может задать своё значение в `.env` и передать его приглашённым отдельно. После смены кода пересоздайте приложение через `docker compose up -d --force-recreate app`. Если переменная пустая, отсутствует или содержит шаблон `replace-with`, регистрация возвращает 503; существующие аккаунты продолжают работать. Код не сохраняется в БД и не отправляется клиенту в данных страницы.

Вход и регистрация через HTML/API используют общий лимитер Better Auth: три запроса за десять секунд на IP и auth path, отказ — 429 с `Retry-After`. В одном процессе состояние хранится в памяти. За reverse proxy настройте доверенное определение IP через `ADDRESS_HEADER`, например `X-Real-IP`; прокси обязан перезаписывать этот заголовок, а порт приложения должен оставаться доступен только прокси. Без этой настройки запросы через один прокси могут делить его IP и общий лимит. Переданные посетителем `X-Forwarded-For` и внутренний `x-viewport-client-ip` сами по себе адрес не определяют.

`ORIGIN` по умолчанию `http://localhost:5173` передаётся в build и runtime. После изменения origin пересоберите образ. Не открывайте приложение по другому hostname: CSRF и Better Auth используют канонический origin.

## Адреса S3

Внутри Compose `S3_ENDPOINT=http://s3:8333` используется для HEAD/GET/PUT/DELETE и настройки bucket. `S3_PUBLIC_ENDPOINT=http://localhost:8333` используется отдельным клиентом только для подписи браузерных ссылок. Оба клиента используют одинаковые bucket/region/credentials; подписанный URL не переписывается после подписи. Это позволяет браузеру обращаться к S3 без знания внутреннего Docker DNS.

CORS разрешает только `ORIGIN`, методы PUT/GET/HEAD и Content-Type, открывает ETag. Anonymous GET возвращает 403. GET TTL — 120 секунд, PUT — до 300 секунд.

## Данные, обновление и остановка

SQLite находится в volume `app-data` по пути `/app/data/viewport.db`; SeaweedFS — в `s3-data`.

```sh
docker compose ps
docker compose logs --tail=50 app
docker compose logs --tail=50 s3
docker compose restart
docker compose up --build -d --wait
docker compose down
```

`down` удаляет контейнеры и сеть, сохраняя volumes. `down -v` удаляет данные. Не запускайте несколько экземпляров приложения с одной SQLite.

Для очистки зависших загрузок после TTL остановите приложение и выполните CLI в одноразовом контейнере:

```sh
docker compose stop app
docker compose run --rm --no-deps app node scripts/cleanup.ts
docker compose up -d --wait app
```

Очистка проверяет по 100 истёкших резервов и по 100 ключей удалённых галерей за запуск. Для большого числа ключей нужны повторные запуски: выбираются давно проверенные ключи. Эти ключи сохраняются бессрочно, поскольку PUT может завершиться после успешного DELETE; при отсутствии новых загрузок запускайте очистку периодически. Отказ DELETE сохраняет ключи для повтора; приложение также очищает до 10 истёкших резервов перед presign и проверяет до 10 ключей удалённых галерей в фоновом проходе после подготовки загрузки. Одновременно выполняется не более одного такого фонового прохода. Ошибка/отмена переводит photo в failed и освобождает квоту; временные ключи удаляются после TTL старого PUT.

## Проверка

```sh
docker compose --profile tools run --rm smoke
```

Профиль tools запускает smoke из того же образа с доступом к SQLite volume. На Linux используется host network, чтобы проверять те же `localhost` URL, которыми пользуется браузер. На Docker Desktop для этой команды нужно включить host networking. Smoke создаёт отдельные аккаунты и удаляет только собственные записи/объекты. Unit tests, типы и сборка: `npm test` и `npm run verify`.

## Разработка с автоматическим обновлением

Для работы с теми же галереями и файлами запустите development-режим Compose:

```sh
docker compose -f compose.yaml -f compose.dev.yaml up --build -d --wait
```

Откройте **http://localhost:5173**. Изменения в `src/` и `static/` подхватываются Vite автоматически; пересборка и перезапуск для них не нужны. При первом запуске создаётся отдельный development-образ; для следующих запусков достаточно `docker compose -f compose.yaml -f compose.dev.yaml up -d --wait`. После изменения `package.json`, `package-lock.json` или `Dockerfile.dev` повторите команду с `--build`. Миграции и S3 настраиваются перед запуском; используются те же volumes `app-data` и `s3-data`, что и в обычном Compose. Compose заменяет приложение, поэтому два процесса не работают с одной SQLite одновременно.

Посмотреть журнал и вернуться к обычному запуску:

```sh
docker compose -f compose.yaml -f compose.dev.yaml logs -f app
docker compose up --build -d --wait
```

Изменения миграций применяются при следующем запуске контейнера. Если настройка Vite или TypeScript менялась заменой файла, пересоздайте приложение той же командой development-режима. На файловых системах, не передающих события изменения в контейнер, может понадобиться polling файлового наблюдателя.

## Разработка на хосте

Нужен Node.js 24 или 26; `.node-version` выбирает Node.js 24 по умолчанию. Если контейнер app запущен, сначала `docker compose stop app`, чтобы освободить порт и исключить несколько процессов. Затем:

Для npm 12 установочные скрипты нужных закреплённых версий `better-sqlite3` и `esbuild` разрешены в `package.json`; после обновления этих зависимостей список разрешений нужно пересмотреть.

```sh
npm ci
npm run db:migrate
npm run s3:setup
npm run dev -- --host 127.0.0.1 --port 5173 --strictPort
```

При этом используется локальный `DATABASE_PATH` из `.env`, а не Docker volume; это независимая БД. S3 может оставаться контейнерным. Для возврата: остановить dev и `docker compose up -d --wait app`.

Compose публикует сервисы только на loopback. Настройка публичного HTTPS и внешнего домена описана в [VP-029](../tasks/issues/VP-029.md), резервное копирование — в [VP-031](../tasks/issues/VP-031.md).

## Лимиты

По умолчанию: 10 МиБ на файл (`MAX_FILE_SIZE_BYTES=10485760`), 5 ГиБ оригиналов на пользователя (`USER_STORAGE_QUOTA_BYTES=5368709120`), до 100 незавершённых резервов на пользователя, до 40 млн пикселей, две обработки одновременно. Браузер принимает большой выбор в очередь и последовательно резервирует файлы перед двумя параллельными передачами. Endpoint партии ограничен `MAX_UPLOAD_BATCH_FILES` (по умолчанию 20, максимум 100). Перегрузка обработки — 429, без фоновой очереди. Уже принятые данные при уменьшении квоты сохраняются; новые загрузки сверх квоты запрещены.

PUT URL — до 300 секунд, reservation — 1800 секунд, GET — 120 секунд. Квота учитывает принятые оригиналы и активные резервы; временные файлы и WebP увеличивают реальный расход S3 сверх квоты. PUT подписывает точный размер файла в `Content-Length` и `Content-Type`: другой размер или MIME-заголовок отвергается S3 с 403. При замене S3-провайдера обязательно повторите smoke; браузерные GET/PUT должны идти напрямую или через прокси, сохраняющий подписанные заголовки и Host. Сервер также проверяет HEAD/GET/декодирование до принятия. Неизменяемые принятые оригиналы находятся под другими ключами, не доступными браузерному PUT.

Для ZIP по умолчанию действуют лимиты `ZIP_MAX_PHOTOS=5000`, `ZIP_MAX_BYTES=5368709120`, `ZIP_MAX_CONCURRENT=3`, `ZIP_TIMEOUT_MS=1800000`. Значения — положительные целые; лимиты параллельности действуют на единственный процесс приложения.

## Восстановление доступа в демо

На странице «Забыли пароль?» пользователь получает инструкцию обратиться к организатору, передавшему приглашение. Организатор подтверждает владельца через известный канал связи; пароль и код приглашения запрашивать не нужно.

При работающем Compose создайте приватный файл внутри контейнера:

```sh
docker compose exec app node scripts/recover-password.ts user@example.test /tmp/viewport-recovery.html
docker compose cp app:/tmp/viewport-recovery.html /tmp/viewport-recovery.html
docker compose exec app rm /tmp/viewport-recovery.html
```

Выберите путь нового файла: CLI отклоняет существующий файл и не перезаписывает его. Передайте файл только подтверждённому владельцу через доверенный канал, затем удалите локальную копию. Файл содержит секретную одноразовую ссылку, не размещайте его в static, репозитории, логах или публичных документах. Срок — 30 минут; повторное использование невозможно. После установки нового пароля все предыдущие сессии отзываются. Публичная отправка ссылок восстановления закрыта; файлы создаёт только CLI организатора. Вошедший пользователь может изменить пароль через «Настройки аккаунта», указав текущий пароль.

## Сборка за TLS-прокси

Если Node.js на хосте уже настроен на корпоративный CA через `NODE_EXTRA_CA_CERTS`, передайте тот же PEM как BuildKit secret `npm_ca` в локальном Compose override. Секрет используется при установке и сборке зависимостей и не включается в образ. Проверку TLS отключать не требуется:

```yaml
services:
  app:
    build:
      secrets: [npm_ca]
secrets:
  npm_ca:
    file: ${NODE_EXTRA_CA_CERTS}
```

Сохраните override в игнорируемом `compose.local.yaml` и запускайте `docker compose -f compose.yaml -f compose.local.yaml up --build -d --wait`. Для development-образа поддерживается тот же build secret.
